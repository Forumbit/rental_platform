# Rental platform

## Запуск

### Подготовка окружения

Понадобятся Go **1.26 или новее**, Docker с Docker Compose v2 и OpenSSL
для генерации ключей. Все команды ниже выполняются из корня проекта.

Создайте `.env` из примера и загрузите Go-зависимости:

```sh
cp -n .env.example .env
go mod download
```

`cp -n` сохраняет существующий `.env`. Для каждого из трёх ключей выполните
команду отдельно и скопируйте полученное значение в соответствующее поле `.env`:

```sh
openssl rand -hex 32
```

Настройте `.env` по примеру `.env.example`:

- `DATABASE_URL` — подключение к PostgreSQL.
- `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` — два разных ключа не короче 32 байт.
  Для каждого ключа сгенерируйте значение командой `openssl rand -hex 32`.
- `SEED_USER_EMAIL` — почта первой учётной записи, по умолчанию `owner@rental.test`.
- `SEED_USER_PASSWORD` — пароль первой учётной записи, от 8 до 72 байт.
- `SEED_USER_FULL_NAME` — имя пользователя, по умолчанию `Rental Owner`.
- `EMAIL_VERIFICATION_SECRET` — отдельный ключ для хеширования кодов,
  сгенерированный командой `openssl rand -hex 32`.
- `PUBLIC_BASE_URL` — адрес API для ссылок из писем. Локально:
  `http://localhost:8080`, на сервере — публичный HTTPS-адрес API.
- `S3_SECRET_KEY` — ключ доступа к хранилищу фото, сгенерированный командой
  `openssl rand -hex 32`. Остальные `S3_*` для локального запуска можно не менять,
  см. [Фотографии объявлений](#фотографии-объявлений).

Также заполните `DB_USER`, `DB_PASSWORD`, `DB_NAME` и `POSTGRES_PORT`.
В примере `DATABASE_URL` собирается из этих переменных. Для проверки регистрации
настройте SMTP по разделу [Отправка почты](#отправка-почты).

### База данных и сервер

Запустите PostgreSQL и хранилище фото (SeaweedFS), дождитесь их готовности,
примените миграции, создайте первую учётную запись и запустите API:

```sh
docker compose up -d --wait
go run ./cmd/migrate -config config/config.yaml -env .env
go run ./cmd/seed-user -config config/config.yaml -env .env
go run ./cmd/api -config config/config.yaml -env .env
```

То же самое короче: `make db migrate seed run`. Первый запуск SeaweedFS
занимает до минуты.

По умолчанию сервер доступен на `http://localhost:8080`. Этот адрес нужно указать
в переменной `base_url` коллекции Postman. Адрес и таймауты задаются в
`config/config.yaml`; переменная `HTTP_ADDRESS` переопределяет адрес.

`seed-user` создаёт подтверждённого пользователя с ролью `user`. Команда идемпотентна:
существующая учётная запись используется со своим прежним паролем и профилем.

### Перезапуск после изменения настроек

После изменения `.env`, конфигурации, шаблона письма или OpenAPI остановите
работающий API через `Ctrl+C` и запустите его снова:

```sh
go run ./cmd/api -config config/config.yaml -env .env
```

Настройки читаются при запуске, а HTML-шаблоны и Swagger встроены в бинарник.
После добавления новых миграций сначала повторите команду `cmd/migrate`.

## Swagger / OpenAPI

После запуска откройте **http://localhost:8080/swagger/**.
Спецификация OpenAPI 3.0.3 доступна по **http://localhost:8080/openapi.yaml**;
исходный файл — `docs/openapi.yaml`.

В Swagger есть все эндпоинты, примеры запросов, схемы ответов и **Try it out**.
После успешного `/auth/login` или `/auth/refresh` access-токен автоматически
подставляется в защищённые запросы. Его можно вставить и вручную через
**Authorize**. Обновлённый refresh-токен нужно скопировать из ответа самостоятельно.
Swagger UI и его ресурсы встроены в Go-бинарник и работают без внешнего CDN.

### Пошаговая проверка регистрации

1. Заполните SMTP-настройки в `.env`, установите `SMTP_ENABLED=true` и
   перезапустите API. Для регистрации используйте настоящую почту, к которой
   у вас есть доступ.
2. Откройте [Swagger UI](http://localhost:8080/swagger/), раскройте
   **POST /auth/register**, нажмите **Try it out**, заполните `email`, `password`
   и `full_name`, затем нажмите **Execute**. Ожидаемый ответ — `201`.
3. Откройте пришедшее письмо. Подтвердите почту одним способом:
   - нажмите **Подтвердить почту** в письме и дождитесь сообщения об успехе;
   - либо в Swagger выполните **POST /auth/verify-email** с `email` и `code`.
     Выберите пример `code`; код передавайте строкой из шести цифр.
4. Выполните **POST /auth/login** с той же почтой и паролем. Ответ `200`
   содержит `access_token` и `refresh_token`. Swagger автоматически установит
   Bearer-авторизацию; сохраните refresh-токен для следующих шагов.
5. Выполните **GET /auth/me**. Проверьте свою почту и `email_verified: true`.
6. Выполните **POST /listings** с примером объявления. Ответ `201` содержит ID
   созданного объявления; с ним можно проверить **GET**, **PUT** и
   **DELETE /listings/{id}**. Черновики видны только в **GET /me/listings**.
   Фото добавляются через **POST /listings/{id}/images**: в Swagger выберите
   файл в поле `image`.
7. Выполните **POST /auth/refresh**, передав сохранённый `refresh_token`.
   Сохраните новый refresh-токен из ответа; новый access Swagger подставит сам.
8. Выполните **POST /auth/logout** с последним refresh-токеном. Ожидаемый ответ —
   `204`. После выхода **GET /auth/me** с токеном этой сессии возвращает `401`.

Если письмо нужно отправить ещё раз, используйте
**POST /auth/verification/resend** с `email`. После повторной отправки используйте
код или ссылку из самого нового письма.

### Быстрая проверка входа с первой учётной записью

Для входа созданным через `cmd/seed-user` пользователем укажите в
**POST /auth/login** значения `SEED_USER_EMAIL` и `SEED_USER_PASSWORD` из `.env`.
По умолчанию почта — `owner@rental.test`, она уже подтверждена.
Далее выполняйте шаги 5–8 выше.

## Отправка почты

### Рекомендуемый сервис: Яндекс Почта

Для отправки с собственной бесплатной почты `@yandex.ru`:

1. Откройте настройки [Почтовые программы](https://mail.yandex.ru/?dpda=yes#setup/client).
   Разрешите доступ по IMAP и включите **Пароли приложений и OAuth-токены**.
2. В [Яндекс ID → Пароли приложений](https://passport.yandex.ru/security/app-passwords)
   создайте пароль приложения типа **Почта**, например с названием `Rental Platform`.
3. Заполните `.env` своим ящиком и созданным паролем приложения:

```dotenv
SMTP_ENABLED=true
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_TLS_MODE=tls
SMTP_USERNAME=your-mailbox@yandex.ru
SMTP_PASSWORD=your-mail-application-password
SMTP_FROM_EMAIL=your-mailbox@yandex.ru
SMTP_FROM_NAME="Rental Platform"
PUBLIC_BASE_URL=http://localhost:8080
```

Для порта **587** используйте `SMTP_TLS_MODE=starttls`. `tls` — TLS с начала
соединения, `starttls` — обязательное переключение на TLS перед авторизацией.
По умолчанию таймаут отправки равен 5 секундам (`SMTP_TIMEOUT=5s`).

Официальная [инструкция Яндекса по SMTP](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others#smtpsetting).

### Если используете Mail.ru

Укажите `SMTP_HOST=smtp.mail.ru`, `SMTP_PORT=465`, `SMTP_TLS_MODE=tls`.
В `SMTP_USERNAME` и `SMTP_FROM_EMAIL` укажите полный адрес своего ящика.
В [Паролях для внешних приложений](https://account.mail.ru/user/2-step-auth/passwords/)
создайте пароль с доступом **Только отправка писем в Почте** и используйте его
в `SMTP_PASSWORD`.

Официальная [инструкция Mail по SMTP](https://help.mail.ru/mail/login/mailer/).

Письмо содержит текстовую и HTML-версию: светлая карточка, шестизначный код и
кнопка подтверждения, без логотипов и внешних изображений. Шаблоны:
`internal/mail/templates/verification.html` и `verification.txt`.

Пока `SMTP_ENABLED=false`, API и вход существующего пользователя работают,
а регистрация и повторная отправка возвращают `503`. После заполнения настроек
перезапустите API.

### Если запрос завершился ошибкой

| Ответ | Что проверить или сделать |
| --- | --- |
| `503` при регистрации или повторной отправке | Проверьте `SMTP_ENABLED`, ящик, пароль приложения, сервер и порт; причина будет в логах API. Если SMTP был выключен, повторите регистрацию после настройки. Если аккаунт уже создан, запросите повторное письмо. |
| `409` при регистрации | Аккаунт с этой почтой уже существует. Войдите или запросите письмо подтверждения. |
| `403` при входе | Сначала подтвердите почту кодом или ссылкой. |
| `400` при подтверждении | Проверьте почту и код из последнего письма. Если код/ссылка истекли, использованы или исчерпаны попытки, запросите новое письмо. |
| `429` при повторной отправке | Подождите число секунд из заголовка `Retry-After`. |
| `401` на защищённом эндпоинте | Выполните вход или refresh и установите актуальный access-токен через **Authorize**. |

Если письмо не видно во входящих, проверьте папку «Спам». Для магической ссылки
`PUBLIC_BASE_URL` должен быть адресом API, доступным в браузере, где открывается письмо.

## Авторизация

| Метод | Путь | Запрос | Результат |
| --- | --- | --- | --- |
| POST | `/auth/register` | JSON с `email`, `password`, `full_name` | `201`: аккаунт создан и письмо отправлено |
| POST | `/auth/verification/resend` | JSON с `email` | `202`: запрос повторной отправки обработан |
| POST | `/auth/verify-email` | `email` + `code` или `token` | `200`: почта подтверждена |
| GET | `/auth/verify-email` | Ссылка из письма с фрагментом `#token=...` | Страница подтверждения |
| POST | `/auth/login` | JSON с `email`, `password` | `200`: пара токенов |
| POST | `/auth/refresh` | JSON с `refresh_token` | `200`: новая пара токенов |
| POST | `/auth/logout` | JSON с `refresh_token` | `204`: сессия завершена |
| GET | `/auth/me` | `Authorization: Bearer <access_token>` | `200`: текущий пользователь |

### Регистрация и подтверждение

`POST /auth/register`:

```json
{
  "email": "your-mailbox@yandex.ru",
  "password": "MyStrongPassword123!",
  "full_name": "Анна Иванова"
}
```

Пароль должен содержать 8–72 байта UTF-8, имя — 1–150 символов.
Роль нового пользователя всегда `user`. Ответ содержит почту и сообщение;
коды и токены подтверждения приходят только в письме.
До подтверждения правильная почта и пароль при входе возвращают `403`.

Для подтверждения кодом вызовите `POST /auth/verify-email`:

```json
{
  "email": "your-mailbox@yandex.ru",
  "code": "001234"
}
```

Код передаётся строкой, чтобы сохранить ведущие нули. Другой вариант — нажать
кнопку в письме: открывшаяся страница подтвердит токен автоматически.
Токен находится во фрагменте ссылки и не попадает в HTTP-запрос или access-логи.
Для проверки ссылки через Swagger передайте в тот же POST-эндпоинт:

```json
{
  "token": "<token из ссылки в письме>"
}
```

Нужно выбрать один способ: `email` + `code` или `token`.
После подтверждения выполните `/auth/login` для получения JWT.

Код и ссылка действуют **15 минут**. Успешное подтверждение отменяет оба способа;
повторное использование возвращает `400`. После **5 неверных кодов** также
потребуется новое письмо. В PostgreSQL хранятся только хеши: SHA-256 для случайного
токена ссылки и HMAC-SHA-256 с отдельным ключом для кода.

Для нового письма вызовите `POST /auth/verification/resend` с `{"email":"..."}`.
Повторная отправка разрешена через **60 секунд**, иначе ответ `429` с заголовком
`Retry-After`. Новое письмо отменяет старые код и ссылку. Для неизвестной или уже
подтверждённой почты возвращается тот же `202`, но письмо не отправляется.
Если SMTP-отправка завершилась ошибкой (`503`), повторную отправку можно запросить
сразу: аккаунт остаётся неподтверждённым, пароль и профиль сохраняются.

Параметры находятся в секции `verification` файла `config/config.yaml`;
переопределения: `EMAIL_VERIFICATION_TTL`, `EMAIL_VERIFICATION_RESEND_INTERVAL`,
`EMAIL_VERIFICATION_MAX_ATTEMPTS`, `PUBLIC_BASE_URL`.

### Вход

`POST /auth/login`, `Content-Type: application/json`:

```json
{
  "email": "owner@rental.test",
  "password": "<значение SEED_USER_PASSWORD из .env>"
}
```

Почта обрабатывается без учёта регистра, пароль — с учётом регистра и пробелов.
Ответ содержит:

```json
{
  "access_token": "<JWT access>",
  "refresh_token": "<JWT refresh>",
  "token_type": "Bearer",
  "access_expires_at": "2026-11-12T10:15:00Z",
  "refresh_expires_at": "2026-11-19T10:00:00Z"
}
```

В Postman сохраните токены в переменные `access_token` и `refresh_token`.
Для защищённых запросов выберите **Authorization → Bearer Token** и укажите
`{{access_token}}`.

### Обновление и выход

Для `POST /auth/refresh` и `POST /auth/logout` используется тело:

```json
{
  "refresh_token": "{{refresh_token}}"
}
```

Обновлению достаточно refresh-токена, в том числе после истечения access-токена.
После успешного обновления сохраните **оба новых токена**. Refresh одноразовый:
повторное использование старого refresh-токена отзывает всю его сессию.
В одной сессии выполняйте обновление одним запросом за раз.

Каждый вход создаёт отдельную сессию. Выход отзывает её access- и refresh-токены;
другие сессии пользователя продолжают работать. Повторный выход с тем же
ещё не истёкшим refresh-токеном также возвращает `204`.

По умолчанию access действует **15 минут**, refresh — **7 дней** с продлением при
обновлении. Сроки, issuer и audience задаются в секции `auth` файла
`config/config.yaml`; доступны переопределения `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL`,
`JWT_ISSUER`, `JWT_AUDIENCE`. JWT подписываются HS256 разными ключами.
Пароли хранятся как bcrypt-хеши, refresh-токены — как SHA-256-хеши в
`refresh_sessions`. Активность сессии проверяется при каждом защищённом запросе.

Ошибки входа возвращают одинаковый `401` для неверной почты и неверного пароля.
Невалидный, истёкший или отозванный токен также возвращает `401`;
некорректный формат запроса — `400`; неподтверждённая почта — `403`.

## API объявлений

| Метод | Путь | Авторизация | Результат |
| --- | --- | --- | --- |
| GET | `/listings?limit=20&cursor=...` | — | `200`: страница опубликованных объявлений |
| GET | `/listings/{id}` | — | `200`: опубликованное объявление, иначе `404` |
| GET | `/me/listings?status=draft&limit=20&cursor=...` | Bearer | `200`: страница своих объявлений в любом статусе |
| GET | `/me/listings/{id}` | Bearer | `200`: своё объявление в любом статусе, чужое — `404` |
| POST | `/listings` | Bearer | `201`: созданное объявление и заголовок `Location` |
| PUT | `/listings/{id}` | Bearer | `200`: полностью обновлённое объявление |
| DELETE | `/listings/{id}` | Bearer | `204`: пустой ответ |

Публичные `/listings` показывают только объявления со статусом `published`.
Черновики и архив автор видит через `/me/listings`. Параметр `status`
(`draft`, `published`, `archived`) необязателен; без него возвращаются все статусы.
Изменять и удалять можно только свои объявления: чужое возвращает `403`.

Списки отсортированы по `id DESC` и используют курсорную пагинацию:

```json
{
  "items": [{ "id": 42, "...": "..." }],
  "next_cursor": 42
}
```

`limit` — от `1` до `100`, по умолчанию `20`. Для следующей страницы передайте
`cursor` = `next_cursor` из предыдущего ответа. `next_cursor: null` означает,
что страниц больше нет. Пустой список — `{"items":[],"next_cursor":null}`.

### Создание и обновление

Тело запроса — JSON, `Content-Type: application/json`. Обязательные поля:
`title`, `description`, `property_type`, `price_minor`, `city`.
`owner_id` и `published_at` задаёт сервер; передавать их в теле нельзя (`400`).

```json
{
  "title": "Уютный загородный дом",
  "description": "Дом с террасой и видом на лес",
  "property_type": "cottage",
  "price_minor": 750000,
  "city": "Истра"
}
```

- `property_type`: `house`, `cottage`, `dacha`, `apartment`.
- `price_minor`: положительное целое число в минимальных единицах валюты
  (`750000` = `7500.00 RUB`). `currency` — трёхбуквенный код, по умолчанию `RUB`.
- `price_period`: `day` (по умолчанию) или `month`.
- `country`: по умолчанию `Россия`.
- `status`: `draft` (по умолчанию), `published` или `archived`.
- `region`, `address`, `area_sqm`, `bedrooms`, `bathrooms`, `max_guests`
  допускают `null` и могут быть опущены.
- `area_sqm`: от `0.01` до `999999.99`, PostgreSQL сохраняет два знака после запятой.
  `bedrooms` и `bathrooms`: `0–32767`; `max_guests`: `1–32767`.
- `published_at` выставляется сервером при переходе в `published`, сохраняется,
  пока объявление опубликовано, и сбрасывается в `null` при переводе в `draft`
  или `archived`.
- `id`, `owner_id`, `created_at`, `updated_at` задаются сервером; `updated_at`
  обновляется при `PUT`.

`PUT` использует тот же формат, что и `POST`: нужно передать все обязательные
поля. Пропущенные необязательные поля сбрасываются в `null` или значение по умолчанию.
Неизвестные поля и несколько JSON-значений в одном теле отклоняются.
Максимальный размер тела — 1 МиБ.

Ошибки возвращаются в формате `{"error":"сообщение"}`:
`400` — неверные данные; `401` — нужна авторизация; `403` — чужое объявление;
`404` — объявление не найдено; `409` — превышен лимит фото;
`405` — неподдерживаемый метод; `413` — слишком большое тело;
`415` — неподдерживаемый Content-Type; `500` — внутренняя ошибка.

| POST | `/listings/{id}/images` | Bearer, автор | `201`: загруженное фото |
| PUT | `/listings/{id}/images/order` | Bearer, автор | `200`: фото в новом порядке |
| DELETE | `/listings/{id}/images/{imageID}` | Bearer, автор | `204`: фото и файл удалены |
| GET | `/images/{key}` | — | `200`: сам файл |

Загрузка — `multipart/form-data` с одним файлом в поле `image`:

```sh
curl -X POST http://localhost:8080/listings/1/images \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -F "image=@photo.jpg"
```

Ограничения (настраиваются в секции `images` файла `config/config.yaml`):

| Что | По умолчанию | Ошибка |
| --- | --- | --- |
| Размер файла | 5 МиБ (`max_size_bytes`) | `413` |
| Фото на объявление | 10 (`max_per_listing`) | `409` |
| Ширина и высота | 8000 px (`max_dimension`) | `400` |
| Формат | JPEG, PNG, WebP по содержимому файла, не по расширению | `415` |

Каждое объявление в ответах API содержит массив `images`, отсортированный
по `position`; первое фото — обложка. Новое фото добавляется в конец.

Чтобы изменить порядок, передайте ID **всех** фото объявления в нужном порядке:

```json
PUT /listings/1/images/order
{ "image_ids": [3, 1, 2] }
```

Если в списке не хватает фото, есть лишние, чужие или повторяющиеся ID, запрос
отклоняется с `400`, и порядок не меняется. Так клиент с устаревшим списком
фото не сможет случайно потерять или перепутать фото. У фото есть `url` вида
`/images/<случайное имя>.jpg`. Файлы отдаёт сам API с кешированием на год:
имя файла случайное и никогда не меняется. Ссылки на фото черновиков видит
только автор. При удалении объявления удаляются и его файлы.

### Хранилище

В Postgres хранятся только метаданные (`listing_images`), сами файлы — в
S3-совместимом хранилище. Локально это [SeaweedFS](https://github.com/seaweedfs/seaweedfs)
из `docker-compose.yml`: бесплатно, файлы лежат в Docker-томе `seaweedfs_data`
на вашем компьютере. Бакет создаётся автоматически при запуске API, наружу
хранилище не открыто: порт `8333` доступен только с `localhost`.

Переменные в `.env`:

- `S3_ENDPOINT` — адрес без схемы, локально `localhost:8333`;
- `S3_ACCESS_KEY`, `S3_SECRET_KEY` — ключи доступа; SeaweedFS берёт их же при запуске;
- `S3_BUCKET` — имя бакета, по умолчанию `listing-images`;
- `S3_USE_SSL` — `true` для облачных хранилищ.

Чтобы перейти на облачное хранилище, достаточно поменять эти переменные:
код работает с любым S3-совместимым сервисом (Cloudflare R2, Yandex Object
Storage, AWS S3 и т. п.). Бесплатные лимиты у сервисов разные — проверьте
актуальные условия перед использованием.

## Деплой (Timeweb Cloud)

```
           HTTPS                    облачный сервер (docker compose)
клиент ───────────▶ Caddy :443 ──▶ api :8080 ──▶ postgres (без внешних портов)
                    сертификат         │
                    Let's Encrypt      ├──▶ S3: бакет с фото
                                       │
                         backup ───────┴──▶ S3: бакет с бэкапами (pg_dump раз в сутки)
```

Фото и бэкапы базы хранятся в S3, поэтому сервер одноразовый: его можно удалить
и за несколько минут поднять заново из последнего бэкапа.

Файлы: `Dockerfile` (образ API), `docker-compose.prod.yml`, `deploy/Caddyfile`,
`deploy/backup/` (скрипт бэкапов) и `.env.production.example`.

### 1. Хранилище S3

1. В панели Timeweb Cloud создайте **два приватных бакета**: для фото
   (`S3_BUCKET`) и для бэкапов (`BACKUP_BUCKET`).
2. Скопируйте ключи доступа (`S3_ACCESS_KEY`, `S3_SECRET_KEY`), а также endpoint
   и регион со страницы бакета. В `.env.production.example` указаны
   `s3.twcstorage.ru` и `ru-1` — сверьте их с панелью.

### 2. Сервер и домен

1. Создайте облачный сервер: Ubuntu 24.04, 1 vCPU, **2 ГБ RAM**, от 20 ГБ диска,
   добавьте свой SSH-ключ. Если есть файрвол, откройте входящие порты 22, 80 и 443.
2. В DNS домена `your-project.site` добавьте A-запись `api` → IP сервера.
   Проверка: `dig +short api.your-project.site` возвращает IP сервера.
   Корень домена остаётся свободным, например для будущего фронтенда.
3. Проверьте на сервере, что исходящий SMTP не заблокирован:
   `nc -vz smtp.yandex.ru 465`. Если соединение не устанавливается, попросите
   поддержку открыть порт — иначе письма подтверждения не уйдут.

### 3. Первый запуск

```sh
curl -fsSL https://get.docker.com | sh
git clone https://github.com/Forumbit/rental_platform.git
cd rental_platform
cp .env.production.example .env
chmod 600 .env
nano .env   # заполните все пустые значения
```

`.env` содержит `COMPOSE_FILE=docker-compose.prod.yml`, поэтому дальше все
команды — обычные `docker compose ...` из папки проекта.

Если в бакете бэкапов уже есть данные (например, сервер пересоздаётся),
**сначала восстановите базу**:

```sh
docker compose up -d --wait postgres
docker compose run --rm backup restore
```

Затем запустите всё:

```sh
docker compose up -d --build
```

Миграции применяются автоматически перед стартом API. Через минуту Caddy
получит сертификат, и API будет доступен по `https://api.your-project.site`,
Swagger — по `https://api.your-project.site/swagger/`.

Первая учётная запись (необязательно): добавьте в `.env` переменные `SEED_USER_*`
и выполните
`docker compose run --rm --no-deps --entrypoint /app/seed-user api -config /app/config/config.yaml`.

### Бэкапы

Сервис `backup` делает `pg_dump` каждый день в `BACKUP_HOUR_UTC` (по умолчанию
03:00 по Москве) и хранит последние `BACKUP_KEEP` копий. Каждый бэкап после
загрузки проверяется: если файл не читается из хранилища, бэкап считается неудачным.

```sh
docker compose exec backup backup.sh backup             # бэкап прямо сейчас
docker compose exec backup backup.sh list               # список бэкапов
docker compose stop api                                 # восстановление:
docker compose run --rm backup restore                  #   последний бэкап
docker compose run --rm backup restore <имя>.dump       #   или конкретный
docker compose start api
```

Восстановление полностью заменяет текущую базу содержимым бэкапа.

### Когда проект не нужен

Перед выключением или удалением сервера **сделайте свежий бэкап**:
`docker compose exec backup backup.sh backup`.

- **Выключить сервер.** Данные и IP остаются на месте, после включения всё
  запустится само. Узнайте в панели, сколько стоит выключенный сервер:
  у разных тарифов диск и IP могут продолжать тарифицироваться.
- **Удалить сервер.** Не платите за него вообще: фото и бэкапы остаются в S3.
  Чтобы вернуть проект, создайте новый сервер, обновите A-запись на новый IP
  и повторите шаг 3 вместе с восстановлением. Платить придётся только за S3.

## Проверки

```sh
make lint   # gofmt и go vet
make test   # все тесты, включая интеграционные с PostgreSQL и SeaweedFS
```

Интеграционным тестам нужен `TEST_DATABASE_URL`. В `.env.example` он равен
`DATABASE_URL`: каждый тест создаёт отдельную временную схему, применяет все
SQL-миграции и удаляет схему после завершения, поэтому данные dev-базы не
затрагиваются. Тест хранилища использует `TEST_S3_*` (по умолчанию те же
значения, что `S3_*`) и отдельный бакет `storage-test`. Перед `make test`
запустите сервисы (`make db`). Без этих переменных интеграционные тесты
пропускаются: `make test-unit`.

Проверяются CRUD и видимость объявлений, курсорная пагинация, права владельца,
`published_at`, загрузка, выдача и удаление фото, все ограничения загрузки
(включая одновременные загрузки сверх лимита), вход, истечение токенов, ротация и повторное использование
refresh, одновременные обновления и выход, очистка устаревших сессий,
регистрация, подтверждение обоими способами, повторная отправка, срок действия,
лимит попыток и одновременное подтверждение. SMTP-тесты проверяют реальные
TLS/STARTTLS-соединения с локальным тестовым сервером, MIME-письмо и отмену отправки.

В GitHub Actions (`.github/workflows/ci.yml`) на каждый push в `main` и pull
request запускаются gofmt, `go vet` и все тесты с PostgreSQL 16 и SeaweedFS.

## Очистка устаревших данных

API раз в `cleanup.interval` (по умолчанию `1h`) удаляет refresh-сессии,
истёкшие или отозванные больше `cleanup.retention` назад (по умолчанию `24h`),
и истёкшие коды подтверждения почты. Настройки — в `config/config.yaml`
или переменных `CLEANUP_INTERVAL` и `CLEANUP_RETENTION`.

Проверка OpenAPI:

```sh
npx --yes @apidevtools/swagger-cli@4.0.4 validate docs/openapi.yaml
```
